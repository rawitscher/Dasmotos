# GP-4821 — Make batch release idempotent and complete the audit trail

**Type:** Bug / Compliance
**Priority:** P1
**Component:** batch-release-service (VALIDATED)
**Reporter:** QA Systems (regulatory finding QA-DEV-337)
**Watchers:** Validation, Manufacturing IT, Internal Audit

## Problem

During the March deviation review, Internal Audit found two issues in the batch
release path:

1. **Double-release on retry.** When the LIMS connector returns `LIMS-BUSY` and
   the client retries, the batch can be posted to LIMS twice, creating duplicate
   release records. In a validated system this is a data-integrity deviation.
2. **Missing audit entry.** The `released` state transition is not written to
   the audit trail, so we cannot produce Part 11 evidence of who released a
   batch and when.

## Acceptance criteria

- [ ] Releasing the same batch twice (same intent) posts to LIMS exactly once
      and returns the original release result.
- [ ] The `released` transition is recorded in the audit trail with actor,
      before/after status, and the LIMS reference.
- [ ] No change to the `LegacyLimsClient` boundary (the mainframe is real).
- [ ] Tests cover: happy path, retry/idempotency, LIMS-BUSY failure, audit entry.
- [ ] Change-control note attached to the PR (validated system).

## Out of scope

- Migrating this service off the legacy connector (tracked separately).
- Label format changes.

## Notes for the reviewer
